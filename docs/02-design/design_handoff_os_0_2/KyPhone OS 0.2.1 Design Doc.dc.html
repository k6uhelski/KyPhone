KYPHONE OS 0.2.1 Design specification · September 2026

A minimal phone prototype designed to get out of the way.

OS 0.2.1 covers the full interface for the Radxa Rock 3A driving an Inkplate 4 over SPI: a 600×600 1-bit panel, a hardware keyboard, and no touch input. It revises 0.2 against emulator testing, which found nine places where the interface had no defined behavior. Each one is now specified.

What changed since 0.2

  • Every list is windowed to a stated row count, so no row is unreachable and the selection is always visible.
  • Sent messages appear in the thread with three states: sending, sent, and not sent, the last with a retry.
  • The message composer wraps to three lines and shows the end of a long draft; Message length is uncapped.
  • An unsaved number reads as a formatted number rather than a truncated one, and its contact page offers SAVE.
  • A new-contact screen replaced the alert, with four validation messages.
  • A contact can be deleted, with a confirmation.
  • CONTACTS moved to third on the home menu, so it is on screen without scrolling.
  • Undrawable characters are rejected at the keystroke, the rule now binds the interface's own labels too, and no control is a silent no-op.

The payload budget

Every screen is drawn from one SPI message of at most 253 characters. The firmware draws what arrives and nothing else, so a list screen can carry only as many rows as fit in 253 characters, however many fit visually. Lists are therefore windowed: only the visible rows are sent, and the window re-sends when the selection moves.

The 24-character preview is a deliberate trade. A 44-character preview costs 69 characters a row and fits only three rows in one payload, which turns the text list into a peephole. Five short previews beat three long ones on a phone whose main screen is the list. The alternative — three rows, full previews — is listed as an open question.

Scrolling rule

One rule for all four lists. The window follows the selection one row at a time: moving past the bottom visible row shifts the window down by one, moving above the top row shifts it up by one. Nothing pages. On e-ink the whole panel flashes on redraw, and a page jump loses the reader's place in a way a single-row shift does not.

The selection can never leave the window, so there is always exactly one inverted row on screen. Arrow up from the first row moves to the header; there is nothing above that. Arrow down on the last row does nothing. The window is its own position cue: the selection is always inside it, so a full window with an inverted row short of the bottom edge says there is more below without spending a band on saying so. The texts and call lists therefore carry no footer at all — the rows run to the bottom edge of the panel. Contacts is the exception: its footer already exists to hold LOOK UP, so it carries the position as 3 / 14 on the right at no extra cost. There is no maximum stored count; the window is what is bounded, not the list.

An empty list is a centered two-line message, not a blank screen: a 24px line naming the emptiness and an 18px line saying what to do — NO CONVERSATIONS over PRESS + TO WRITE THE FIRST MESSAGE. A filter that matches nothing says NO MATCH over NO NAME STARTS WITH THAT. PRESS BACKSPACE TO WIDEN THE SEARCH.

Message states

A message the user sends appears in the thread immediately, right-aligned with a tail on its right edge, and stays there. The fill carries the state, and the label under the bubble names it:

State Bubble Label at 18px
Sending2px outline, paper fillSENDING...
Sentfilled with ink, paper textSENT 6:53 PM
Not sent2px outline, paper fillNOT SENT, in bold

A filled bubble means the message left the phone. An outlined one on the right means it has not, which is why not-sent needs no icon to read as unfinished. Sending and not-sent share a treatment because they share a fact; the label separates them, and sending is transient.

Retry. Arrow up from the composer selects the newest not-sent message rather than jumping to the header: it is the only thing in a transcript worth selecting. The selected bubble gains a second ink line 3px inside its border, drawn within the border box so it never meets the tail, and its label becomes NOT SENT - ENTER TO RETRY. Enter returns it to sending. Arrow up again reaches the header, arrow down returns to the composer. With no not-sent message present, arrow up goes straight to the header as before.

There is no cellular service in this build, so not sent is the normal outcome and the design is written for it rather than treating it as the error case. A new conversation joins the text list on the first send whether or not it succeeded, and its row preview carries a leading ! in place of You: while the last outgoing message is unsent.

The phone has no notion of its own number, so it can never key a thread to itself. A thread is keyed on the other party's number, and nothing in the interface displays or refers to the phone's own number — there is nothing to filter and nothing to show.

Long text and character limits

Composer. The thread composer wraps to at most three lines of 24px text and grows upward from the bottom edge: 45px tall at one line, 79px at two, 113px at three, with its 2px rule riding the top of the block and the message area shrinking to match. When the draft is longer than three lines the composer shows the end of it behind a leading ..., so the cursor is always visible and the user can always see what they are typing. The device fits 30 characters of 24px text across the 552px composer, so the visible tail is 87 characters.

Message length. Uncapped, and no counter anywhere. 160 characters would be one GSM segment, which only means something once a radio is attached; until then a limit buys nothing and costs the user a sentence. Nothing in the interface counts characters for the user.

Bubbles. A bubble wraps to as many lines as the message needs, at 26 characters a line. The message area is bottom-anchored and shows at most three bubbles, so a long message pushes older ones off the top, and a message longer than the area runs off the top of its own bubble with its newest lines against the composer. That is the rule the transcript already follows: the bottom of the screen is the present. Nothing is truncated inside a bubble — a message that cannot be read in full is worse than one that pushes an older message off screen.

Allowed characters. Printable ASCII, 32 to 126, less two: | and · are reserved as field separators in the SPI payload. Any other keystroke — an emoji, a curly quote, a dead key — is ignored: nothing appears and no alert fires, because a rejected keystroke is not an error worth a screen. Received text is not under our control, so an undrawable character in an incoming message is drawn as ?.

The rule binds our own labels. No interface string may use a character the panel cannot draw, which rules out the ellipsis character, the em dash and the middot — the three a designer reaches for by habit. So: SENDING..., NOT SENT - ENTER TO RETRY, ENTER ACCEPT / ESC DECLINE, and ... as the composer's truncation prefix. A label the panel cannot draw is the same defect as a keystroke it cannot draw, and nothing sanitizes a literal. The quote list in kyphone_os.py needs the same pass: one entry carries an em dash today.

Unsaved numbers

A number that is not in the address book is displayed formatted, never truncated: (555) 019-9002. Ten digits, or eleven beginning with 1, format to that pattern; anything else is shown as typed. The formatted form is 14 characters, which is the name column's width on the texts list and the call list, so two unsaved numbers that share a prefix are never identical on screen.

The contact page for an unsaved number puts the formatted number in the 48px title slot and NOT IN CONTACTS in the 24px line under it. Its action row is CALL, TEXT, SAVE, and the header's right control is empty, since there is nothing to edit yet. SAVE opens NEW CONTACT with the number already in the phone field and the cursor in FIRST NAME.

A saved contact with no number is the mirror case: the name in the title, NO NUMBER SAVED beneath it, and a single ADD NUMBER button in place of CALL and TEXT, because neither can be performed.

New contact

The new-contact screen is the edit form with blank fields and the title NEW CONTACT. It has no DELETE button, which is the only difference between the two. It is reached from the + in the contacts header, and from SAVE on an unsaved number's contact page, which prefills the phone field.

X or Escape returns to wherever the form was opened from: the contacts list, the contact page, or the compose screen. Saving lands on the new contact's own page, so the user sees what they created. The exception is the compose picker: saving there returns to compose with the new contact in the TO field, because the user was in the middle of writing a message and the contact was a step along the way.

Validation. Four checks, each a stop alert in the existing style — boxed exclamation, 24px prose, OK bottom right — titled CONTACT, returning to the form with the offending field selected:

  • A CONTACT NEEDS A FIRST NAME. TYPE ONE IN THE FIRST NAME FIELD, THEN PRESS SAVE.
  • A CONTACT NEEDS A PHONE NUMBER. TYPE ONE IN THE PHONE NUMBER FIELD, THEN PRESS SAVE.
  • THAT NUMBER CANNOT BE DIALED. A NUMBER NEEDS TEN DIGITS, OR ELEVEN STARTING WITH 1. SPACES, DASHES AND BRACKETS ARE FINE.
  • THAT NUMBER IS ALREADY SAVED AS PIP OKONKWO. EDIT THAT CONTACT INSTEAD, OR TYPE A DIFFERENT NUMBER.

Last name is optional. The number field accepts digits and + ( ) - . and spaces while typing, and is stored in the formatted form. Duplicates are detected on the last ten digits, so (917) 555-0101 and +1 917 555 0101 are the same person.

Deleting a contact

DELETE sits at the bottom left of the edit form, as a 2px-bordered button opposite SAVE. It is on the form rather than the contact page because the contact page is where you act on a person and the form is where you change the record; deletion is a change to the record. Arrow left from SAVE reaches it. The alternative — a third button on the contact page — is listed as an open question.

Confirmation uses the discard dialog's layout with its own words: title DELETE CONTACT, body DELETE PIP OKONKWO? THE MESSAGES STAY IN THE TEXT LIST, LABELED WITH THE NUMBER. THE NAME CANNOT BE BROUGHT BACK. The destructive button, DELETE, sits bottom left with a 2px border; the safe button, KEEP CONTACT, sits bottom right with a 3px border and holds the selection when the screen opens.

Rule for every confirmation. The safe choice is the right-hand button, it carries the 3px border, and it is selected when the screen opens. The destructive choice is on the left with a 2px border and is never the default. Escape is the safe choice too.

Deleting leaves that person's conversations alone. A thread is keyed on the number, so the row simply falls back to the formatted number — no thread disappears, and nothing is orphaned.

Smaller items

Home menu order. TEXT, CALL, CONTACTS, READ, LISTEN. Contacts moved to third so it is on screen on first view; READ and LISTEN are stop alerts in this build and cost nothing by sitting below the fold. The alternative — keeping the original order and strengthening the scroll cue — is available in the prototype as a tweak.

No silent no-ops. SEND with an empty message raises THERE IS NOTHING TO SEND. TYPE A MESSAGE FIRST, THEN PRESS SEND. SEND with no recipient raises THERE IS NO ONE TO SEND THIS TO. TYPE A NUMBER IN THE TO FIELD, OR PRESS + TO PICK A CONTACT. Saving a blank form raises the validation alerts above. The only deliberate silence in the interface is a rejected keystroke.

Decisions taken after the emulator test

  • Five rows over three. The texts list keeps five rows with 24-character previews rather than three with the full 44. The list is the main screen and its job is to be a list.
  • No message cap. Nothing limits or counts message length.
  • No own number. The phone does not know or display its own number.

Open question

Delete placement. DELETE is specified on the edit form, bottom left opposite SAVE. The alternative is a third button on the contact page, next to CALL and TEXT. One decision outstanding.

Type scale

Unchanged from 0.2. The Adafruit GFX built-in font draws a 5×7 glyph in a 6×8 cell and scales only by whole multiples, so the scale is built from those multiples.

Ink, headers, buttons, alerts

Unchanged from 0.2. Two values, no grays: ink is #111111, paper is #FFFFFF. Selection is inversion. Rules are 1px within a list and 2px where a region ends. Every list screen carries a three-part header — back left, screen name centered, the one additive action right — each control a 38×34 hit box that inverts when selected. A button is a 3px-bordered box, and the default is the safe one. An unbuilt screen is a stop alert that says what happened, why, and what to do instead.
